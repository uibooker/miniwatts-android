# Xiaomi 15 / dada：下一阶段推进方案

日期：2026-10-13。依据[控制与恢复主审](DADA_NEXT_RESEARCH_REVIEW.md)、[独立请求恢复边界](DADA_NEXT_RESTORE_RESEARCH.md)及[开源方案对照](GITHUB_ANDROID_BYPASS_RESEARCH_REVIEW.md)。本文是推进方案，没有发现新的可用接口，没有修改插件，没有执行手机读取、写入、安装、驱动加载或实机试验。

**下一阶段先完成“能否取得足够资料实现机型专用后端”的决策。** 已定位充电使能候选链，但仍未证明当前机型停充后保留系统输入供电。现有用户入口缺少插件请求撤销方式，软件成功返回也不能证明硬件成功。不能将这三项问题合并成“只差一个关闭按钮”。

## 第一阶段：资料与可用接口，全部在电脑进行

从已取得的驱动 ELF、远端固件和构建记录出发，只针对明确缺口补资料，不重复泛搜旁路模块或遍历节点数值。

| 工作 | 需要取得或证明的内容 | 阶段交付物 |
| --- | --- | --- |
| 厂商现有完整入口 | 核对与当前构建匹配的 MiCharge/HAL 接口定义或二进制，是否存在申请、查询和释放充电请求的方法；逐项跟到实际 MCA voter/provider。名字为 disable/reset、方法存在或返回成功都不足以证明撤销 | 入口清单，区分已证实、已排除和缺资料；每个候选注明实际对象、参数、错误处理、副作用和恢复语义 |
| 自建接口的可行性 | 若厂商没有可用完整入口，再核对 MCA 实际源码、头文件、锁/生命周期；涉及构建驱动时才进一步要求匹配配置、工具链、Module.symvers、ABI 和加载策略。官方 MCA symlink 本身不满足这些要求 | 是否具备构建受限控制接口的条件；缺项应指明具体材料，不把 root 或模块 build-id 匹配当作可加载保证 |
| 供电与附带动作 | 取得匹配 PMIC 型号/修订的字段定义、HAL 表和板级供电资料，闭合 charge enable、输入控制、buck 与快充/CP 的模式转换；核实远端附带操作和恢复要求 | 受影响状态及转换表；说明哪些条件可以保留输入供系统，哪些条件会改变输入或快充，以及仍缺何种运行身份信息 |
| 测量可信度 | 核对拟用 show/getter 的错误处理、单位、符号、测点、采样年龄、校准和读副作用；排除默认值、USB ADC 无匹配和电流置零 flag 的误判 | 可用测量清单和不可用原因；把软件请求、聚合状态、硬件状态和物理测量分开记录 |

当前电脑材料中已有 MCA 模块和远端固件；本阶段没有取得匹配的厂商用户态 HAL 实现。应先确认其资料来源，不能把 HAL 核查写成已完成。若需要同构建固件包，先用已有构建记录确定版本与包的对应关系；无需为此先安装或替换手机组件。

本阶段必须得出可判断的结果：找到完整原生入口，或证明具备修改匹配驱动的资料条件，或列明使这两条路线暂不能继续的具体缺项。已分析材料无法填补某项缺口时，在该缺口结束该条线，不通过扩大不具名函数扫描、借用其他 voter 的 owner 或套用相似芯片偏移替代证据。

## 第二阶段：确定恢复契约，再实现后端

优先采用经证实的厂商完整入口；其不存在或不满足要求时，才评估修改匹配驱动或新增受限驱动接口。没有准确类型、对象生命周期和硬件定义时，不编写靠猜结构/地址的可加载扩展。

第一版恢复目标可采用**功能恢复**：固定插件 owner 不再参与聚合，原生策略重新掌握控制，受影响的硬件及远端附带状态得到恢复确认。允许留下一个固定、已禁用的客户端名字；不必每次删除名字。最多 32 个槽位的约束仍需处理，不能每次新建 owner。

这一收窄不会让现有 `charge_enable` 变得可用：它仍然没有 enabled=0 用户参数。写 active allow=1 不能替代撤销。已有按 owner 查询还可能分配槽位，不能用它们拼出无副作用原态快照。若未来要求原始 absent/inactive/active 和 stored value 全部一致，需要另行满足严格状态恢复。

受限接口应围绕三项操作设计：

1. **查询：** 不改变控制状态，说明 owner 是否存在、是否有效，以及软件状态和硬件确认各自的有效性。
2. **申请：** 只允许预定的插件 owner 和已审查的控制对象；与其他原生策略并存；拒绝未知原态和不支持的模式转换。
3. **释放：** 撤销自身约束，重新聚合并确认受影响状态的恢复；记录真实错误。断连、超时、进程退出、重启及并发的处理必须有明确实现，不能假定失败意味着远端没有执行。

资料与契约通过后，在电脑上实现并检查状态机。必要验证应覆盖申请失败、部分执行、软件缓存与硬件不一致、重复申请、释放失败、连接变化和并发策略；这些检查验证程序与恢复逻辑，不计为电气旁路验证。

## 第三阶段：建立可审阅的实机方案

先为每个拟读接口给出 show/getter 审查证据。只读命令也可能调用硬件，不能仅因命令叫 cat 就纳入采样。通过审查后，才列出精确的手机读取白名单和运行身份核对方法；新 getter 不自动获准使用。

控制验证方案需包含确定的接口与参数、进入条件、原状态记录、退出与失败恢复步骤、观测字段和终止条件。控制与恢复尚未闭合时，没有合格的试写方案，不交付让用户自行尝试的开关命令。

方案具备条件并经用户确认后，进行一次预先限定的正常充电 / 候选控制 / 恢复对比。比较应保持电量、温度、充电器和负载条件可比，同时确认：

- 外部输入在控制期间仍承担系统负载。
- 电池在稳态没有持续净充电或持续净放电；明确仪表误差、瞬态和电池缓冲参与的解释。
- buck、快充/CP、插件 owner 和相关附带状态符合预期，退出后原生策略恢复。

充电功率降低、SOC 不升、软件 flag=1、USB online=1 或单次电池电流=0 均不能单独判定成功。若只验证了限流或暂停输入，报告应如实分类，不能包装成旁路。

## 完成与停止条件

只有上述控制、供电、测量和恢复证据齐备并通过对比，才把旁路后端加入 SukiSU 插件。现有插件在此前仍按 FCC 限流能力评价。

若当前构建的必要资料不可取得，且没有完整厂商入口，应交付“当前资料不足以安全实现”及具体缺项；保留已完成的诊断成果，不靠未审查写入、第三方内核替换或直接寄存器操作继续试验。这个停止点说明当前实施条件不足，不证明硬件永远不能支持。
